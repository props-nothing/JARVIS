# Storage and Data Architecture

Status: PROPOSED

## Storage Profiles

### Local Profile

- SQLite is the canonical transactional store.
- Local application files hold large artifacts and backups.
- OS keychain holds provider credentials where available.
- No database server, cache, vector service, or container is required.

### Server Profile

- PostgreSQL is the canonical transactional store.
- pgvector supports vector indexes where justified.
- S3-compatible object storage holds large immutable artifacts.
- A production secret manager resolves credential references.
- Redis or another cache is optional and must not own canonical state.

Both profiles implement the same application ports and semantic contract. They
may differ in scale and query strategy, not user-visible correctness.

## Data Ownership

| Data | Canonical owner | Examples |
| --- | --- | --- |
| Identity/config | JARVIS database | users, workspaces, devices, grants |
| Conversation/run state | JARVIS database | sessions, messages, runs, steps |
| Memory | JARVIS database | memories, entities, relations, provenance |
| Tool/workflow state | JARVIS database | calls, approvals, workflows, jobs, events |
| Connector state | JARVIS database | accounts, cursors, webhook inbox |
| Runtime state | Runtime plus JARVIS reference | opaque checkpoint, runtime instance |
| Large content | Object/file store plus database metadata | attachments, audio, documents, artifacts |
| Secrets | Secret store | API keys, OAuth refresh tokens, signing keys |
| Cache | Rebuildable only | discovery, rankings, model catalogs |

If losing a cache would lose user intent, approval, memory, or task progress,
the data was misclassified.

## Repository Ports

Repositories expose purpose-specific operations with explicit scope. A method
that reads workspace-owned data requires a `WorkspaceId` and authorization
context or receives a pre-authorized application context that cannot be forged
by adapters.

Avoid generic table CRUD. Use methods such as:

```rust,ignore
trait RunRepository {
    async fn create(&self, run: NewRun) -> Result<Run, StorageError>;
    async fn transition(&self, transition: RunTransition) -> Result<Run, StorageError>;
    async fn load_for_resume(
        &self,
        workspace: WorkspaceId,
        run: RunId,
    ) -> Result<Option<RunResumeState>, StorageError>;
}
```

Transition methods enforce expected version/state and return conflict rather
than silently overwriting concurrent work.

## Transactions

Atomic use cases use an application unit-of-work port. Required examples:

- transition run state and append its durable activity event;
- reserve a tool call and consume a one-shot approval;
- persist tool outcome and enqueue outbox event;
- update workflow step and schedule its next wake-up;
- commit memory correction and supersession relation;
- store webhook inbox dedupe key and enqueue normalized event.

Do not place network calls inside database transactions. Use pending/attempt
records and reconciliation for external effects.

## IDs and Time

- Use UUIDv7 or another sortable, globally unique typed ID after crate/version
  research confirms support.
- IDs are generated by an injected port for deterministic tests.
- Store timestamps in UTC with sufficient precision and explicit semantics.
- Inject a clock; timers and expiry tests never depend on wall-clock sleeps.
- Preserve external provider IDs in scoped columns; never use them as globally
  trusted primary IDs.

## SQLite Profile

Target configuration:

- WAL mode where platform/filesystem behavior is verified;
- foreign keys enabled;
- busy timeout and bounded write retry;
- one controlled write path or writer pool sized for SQLite reality;
- explicit checkpoint/backup behavior;
- integrity check in doctor/restore flows;
- owner-only filesystem permissions and Windows ACL validation;
- no database file on unsupported network filesystems without warning.

Migration and backup tests must use real SQLite files, abrupt termination, and
previous supported schemas.

For local search, begin with FTS5. If semantic search is needed before a stable
cross-platform SQLite vector extension is selected, store versioned embeddings
and perform a bounded application-side scan over an explicitly capped candidate
set. Never load an unbounded memory corpus into RAM.

## PostgreSQL Profile

Target configuration:

- SQL transactions and row constraints mirror domain invariants;
- workspace/principal filters are mandatory in queries;
- optional row-level security is defense in depth, not a substitute for
  application authorization;
- advisory locks or lease rows coordinate singleton jobs where appropriate;
- `FOR UPDATE SKIP LOCKED`-style job claims are evaluated for workers;
- pgvector indexes are selected from measured corpus/recall needs;
- connection pools are bounded per process and expose saturation metrics;
- migrations support rolling deployment only when server mode needs it.

## Migrations

Every schema migration has:

- monotonically ordered immutable migration ID;
- supported source versions;
- transactional behavior documented per backend;
- precondition and postcondition checks;
- data transformation tests with realistic volume;
- backup requirement and rollback/forward-fix plan;
- compatibility impact on old/new binaries;
- doctor diagnostics for partial or unsupported states.

Persisted JSON/protobuf payloads have their own schema version; a table migration
does not automatically migrate opaque payload semantics.

## Outbox and Inbox

The outbox is written in the same transaction as canonical state. A dispatcher
publishes events at least once and marks delivery after success. Consumers use
event IDs and handler-version-aware inbox records to deduplicate.

An outbox row is not deleted before retention/audit requirements are met. Large
payloads are referenced by content-addressed artifacts rather than duplicated.

## Objects and Artifacts

Artifact metadata records:

- artifact ID, workspace, owner, media type, byte length, hash;
- sensitivity, retention, encryption profile, and provenance;
- logical purpose and related run/tool/call/document;
- storage backend/key without signed download credentials;
- creation, access, expiry, and deletion state.

Validate type from bytes where security matters. Names and MIME types supplied
by users or providers are not trusted. Downloads use short-lived scoped access.

## Backup and Restore

Backups include a manifest with JARVIS version, schema versions, profile, hashes,
encryption metadata, included/excluded secret references, and creation time.

- Backups never silently include OS keychain secrets.
- Restore validates all hashes and supported versions before mutating active data.
- Restore targets a new profile by default; in-place restore requires explicit
  confirmation and pre-restore backup.
- Cross-profile restore maps unavailable secrets/connectors to reauth-required.
- A successful backup is not proven until restore is tested.

## Data Deletion

Deletion is a workflow, not one SQL statement. It tracks canonical records,
objects, search indexes, caches, provider-side resources where applicable,
backups/retention exceptions, audit obligations, and completion evidence.

User-visible "forget" semantics must distinguish context exclusion, soft
archive, hard deletion, and legally retained audit metadata.
